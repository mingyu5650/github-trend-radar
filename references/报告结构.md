# 报告结构

## 九个固定章节

每个排行榜都同时列出统计周期和数据源；数值缺失时显示降级，不推导或重排模型数据。

1. **今日速览**：分别列 `facts`、`inferences`、`actions`。事实写入查询时合并后的项目数量；分类报告另列分类筛选条件。推断不得冒充来源事实。
2. **核心排行榜**：
   - “用途与定位”和“主要解决问题”必须输出中文；产品名、协议名和必要技术术语可保留原文。英文官方简介存在人工校准中文覆盖时使用覆盖，否则回退到中文分类摘要，不直接拼接英文简介。
   - 总 Star 表列：序号、仓库、一级分类、仓库类型、用途与定位、主要解决问题、当前累计 Star（个）、数据口径；来源 GitHub Search，周期为查询时累计值。
   - 24h 新增表列：序号、仓库、一级分类、仓库类型、用途与定位、主要解决问题、当前累计 Star（个）、过去24小时新增 Star（个）、数据口径；当前累计 Star 来自本次查询合并后的 GitHub 仓库记录，增量来源为 OSSInsight 24h external 或有效 local history 24h。
   - 7 日新增表列：序号、仓库、一级分类、仓库类型、用途与定位、主要解决问题、当前累计 Star（个）、过去7天新增 Star（个）、数据口径；当前累计 Star 来自本次查询合并后的 GitHub 仓库记录，增量来源为 OSSInsight 7d external 或有效 local history 7d。
   - 有有效 local 数据时增加“增长加速度”表：序号、仓库、一级分类、仓库类型、用途与定位、主要解决问题、24h增速相对7日日均（倍）、数据口径；计算为最近24小时新增除以最近7天平均每日新增，Markdown 展示统一保留两位小数，JSON 保留原始数值精度。
   - 24h/7日增量以 `+N` 表示统计窗口内新增约 N 个 Star；它不是累计 Star、评分或排名。
3. **分类趋势**：表列分类、事实、上期变化、可信度。来源为查询时客观 selected set；分类计数不纳入 watchlist-only 项目。
4. **可复用项目榜**：表列仓库、用途与定位、主要解决问题、描述来源、当前累计 Star（个）、可复用内容、接入形式、评分、许可证、维护、风险、动作。所有描述项必须使用中文，产品名、协议名和必要技术术语可保留原文。用途与问题优先提取官方中文 README 的 Features/特性和 Use Cases/应用场景；英文 README 仅在存在人工校准的中文覆盖时用于详细描述，否则回退到中文分类摘要，并在描述来源中明确标识。README 不可用时同样回退到分类摘要。当前累计 Star 使用本次查询合并后的 GitHub 仓库记录，缺失时明确显示降级，不使用增长值代替。表格上方必须说明评分权重、缺失信号按 0 分、评分仅作筛选线索，以及维护状态阈值（90 天内活跃、91–365 天需复核、超过 365 天低活跃，另列已归档与信息不足）。来源为查询时 selected set、GitHub README 与 GitHub 详情；只展示可运行/可采用项目，评分与热度分开。
5. **重点项目解读**：最多 5 个项目；每项列事实、推断、证据、可信度、行动建议。来源为本期 GitHub 总榜候选及其来源记录；不得用篇幅凑足五项。
6. **历史热门、退榜与替代**：表列仓库、事实、推断原因、证据、可信度、替代关系、行动建议。比较当前查询与最近历史快照；明确“退榜不等于过时”，没有 canonical 证据不得输出直接替代。
7. **市场走向**：表列结论、具体数据证据、上期变化、可信度、连续周期。只使用标明来源且周期可比的数据；没有具体数据证据时留空或降级，不写市场结论。
8. **个人观察清单**：表列仓库、观察理由、下一步动作。来源为当前 Excel 观察清单；该章可包含 watchlist-only 项目，但不得反向污染前述客观章节。
9. **数据口径与异常**：表列项目、说明；汇总本次查询的所有来源状态、查询时间、查询周期及 external/local 口径，并按实际情况列缺失、降级与警告、冲突、人工推断。

## JSON 核心 keys

唯一的顶层核心 keys 为：`metadata`、`overview`、`rankings`、`category_trends`、`reusable_projects`、`featured_projects`、`history`、`market_trends`、`watchlist`、`data_quality`、`repositories`。

- `metadata`：`date`、`query_time`、`periods`、`ranking_sources`、`source_status`。
   - `rankings`：`total`、`daily`、`weekly`、`acceleration`；每行保留 `repo`、`value`、`source`、`data_scope`、`metric_name`、`unit`、`description`、`primary_category`、`repository_type`、`purpose`、`problem_solved`。
- `rankings.daily` 与 `rankings.weekly`：除通用榜单字段外，保留 `total_stars` 作为本次查询时的当前累计 Star；`value` 仍只表示对应窗口内的新增 Star。
- `repositories`：selected set 的标准仓库记录与 `source_records`，不包含仅由观察清单补入的仓库。
- 其余 keys 与九章节一一对应；不要创建平行别名作为第二套报告结构。

## 目录与成功语义

默认根目录为 `GitHub开源趋势雷达/`；`--workspace /path` 时根目录为 `/path/GitHub开源趋势雷达/`。日期取 `Asia/Shanghai`。

```text
GitHub开源趋势雷达/
├── 配置/
│   ├── 分类规则.yaml
│   └── 项目观察清单.xlsx
├── 最新报告/
│   ├── GitHub开源趋势与项目复用雷达-YYYY-MM-DD.md
│   ├── GitHub开源趋势与项目复用雷达-YYYY-MM-DD.html
│   ├── 原始数据-YYYY-MM-DD.json
│   ├── GitHub开源趋势与项目复用雷达-分类-<分类>-YYYY-MM-DD.md
│   └── 原始数据-分类-<分类>-YYYY-MM-DD.json
├── 历史归档/YYYY/MM/YYYY-MM-DD/
│   ├── GitHub开源趋势与项目复用雷达-YYYY-MM-DD.md
│   ├── GitHub开源趋势与项目复用雷达-YYYY-MM-DD.html
│   ├── 原始数据-YYYY-MM-DD.json
│   ├── GitHub开源趋势与项目复用雷达-分类-<分类>-YYYY-MM-DD.md
│   └── 原始数据-分类-<分类>-YYYY-MM-DD.json
└── 运行状态/
    ├── 历史指标/
    │   └── YYYY-MM.jsonl
    └── 锁/
        └── 业务目标稳定哈希.lock
```

同一上海日期再次成功运行完整报告时，覆盖完整日报的当日归档报告/JSON 及 `最新报告/` 下同日期的报告/JSON，并按 `date + repo` 更新当月 JSONL。保存分类报告时，只覆盖该分类同日期的文件，不覆盖完整日报文件。`最新报告/` 只保留最近一次成功提交对应日期的完整日报报告/HTML/JSON（及同日期分类文件，如有）；不得保留更早日期文件，也不得额外维护 `*-最新.*` 别名副本。完整日报文件存在不表示 history 与 Excel 后置更新必然成功。归档成功但对应日期文件保存失败时保留原文件，且不写 history/Excel。

无分类的完整 `report` 默认保存并更新全局 history，且只更新 Excel M–P。`report --category <固定一级分类>` 默认只预览；增加 `--save` 后仅保存独立分类归档与分类日期报告对，不写全局 history，不更新或创建 Excel。`repo`、`compare` 不持久化；`watchlist` 只处理观察清单自动列。
