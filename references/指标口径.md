# 指标口径

## 来源矩阵

| 来源 | 可用事实 | 作用域与周期 | 状态边界 |
| --- | --- | --- | --- |
| GitHub Search | 当前累计 `total_stars`、创建/推送时间、语言、许可证等 | 客观总 Star 候选集；查询时点值 | `github_top`，不得代表增长来源 |
| GitHub Repository/Release | 单仓详情、最新 Release、维护元数据 | 单仓补全 | `github_details` 或 `watchlist_details`；Release 失败独立记录 |
| GitHub README | Features/特性与 Use Cases/应用场景章节中的项目自述 | 可复用榜用途、功能与场景补全 | `github_readme`；不可用时回退到分类摘要，不补造能力 |
| OSSInsight | `stars_24h_external`、`stars_7d_external` | 各自的 selected set 与精确周期 | `ossinsight_24h`、`ossinsight_7d` 分开判断，禁止互相代替 |
| GitHub Trending | 页面累计 Star 与该页面标明的周增 | weekly selected set，仅作发现集合 | `github_trending_weekly`；不是 GitHub 全量排行榜 |
| 本地历史快照 | `stars_24h_local`、`stars_7d_local`、增长加速度 | 仅在有效基线窗口内计算 | 与 external 分字段、分来源展示 |
| 观察清单 | 人工关注理由、使用状态及自动检查结果 | 跟踪集合，不是客观发现源 | watchlist-only 项目不得进入客观榜、分类计数或复用榜 |

任何来源只对自身周期负责。某来源/周期降级时，保留其他来源的有效结果并显示状态；不得把别的周期或 `created_at` 伪装成缺失增长。

## 热度指标

- **总 Star**：查询时 GitHub 当前累计值；只按 GitHub Search 的累计值排序。
- **created_at**：仓库创建日期，仅作元数据，绝不代表 24h/7d 新增。
- **24h 新增**：优先采用 `stars_24h_external`；缺失时仅可采用有效的 `stars_24h_local`，并保留来源标签。
- **7d 新增**：优先采用 `stars_7d_external`；缺失时仅可采用有效的 `stars_7d_local`，并保留来源标签。
- **本地有效窗口**：24h 基线年龄必须在 18–30 小时；7d 基线年龄必须在 144–192 小时。选择最接近 24/168 小时的基线；等距时选较新的基线。无有效基线则返回缺失，不外推。
- **增长加速度**：`24h local ÷ (7d local ÷ 7)`。仅当两项 local 都存在且 7d local 大于 0 时计算；它比较最近一天与七日平均日增，不是绝对增长量。

## 分类与仓库类型

一级分类固定为：`AI`、`开发工具`、`基础设施与 DevOps`、`数据与数据库`、`安全`、`前端与 UI`、`移动端`、`其他`。配置只能调整一级分类的匹配规则、增加或调整二级标签，以及对合法仓库做人工覆盖；不得增加、删除或改名一级分类。

二级标签可配置且可多选，例如 AI Agent、Coding Agent、MCP、RAG。`repository_type` 独立描述物料形态：Awesome 清单、教程或课程、书籍或资料、数据集、模型、模板、SDK 或库、可运行软件。

客观热度榜允许展示发现集合中的不同仓库类型，并显式列出类型；复用榜回答可采用性，排除 `runnable=false` 及信息/资料/教程/聚合/榜单类仓库。不要把“热”直接等同于“可复用”。

## 复用评分

七项权重总计 100：许可证 20、维护 20、文档 15、Release 15、集成 15、社区 10、CI 5。除许可证外，信号使用 0–1 比例；缺失信号按 0 计，并标记“部分复用信号缺失”。维护、Release 与社区信号来自仓库详情、推送时间、Release 和 fork/Star 比例；文档、集成与 CI 是基于官方简介长度、topics、仓库类型和主要语言的元数据启发式信号，不代表完成了文档质量、集成成本或 CI 工作流审计。CI 仅在 topics 含 CI/CD 标识时得分；详情已获取但没有标识时记为 0。报告 JSON 必须保留评分信号、分项得分、缺失信号和信号覆盖置信度，便于复核，不得补造仓库能力。

硬风险至少包括“许可证不明确”和“仓库已归档”。评分是筛选线索，不是采用结论；同时报告信号覆盖置信度、维护状态、许可证和风险。

## 降温、退榜与替代

降温检测支持五类触发：

1. 上期前 20 本期退出前 50；仅当本期客观总榜覆盖至少 50 个仓库时才可确认。
2. 可比增长相对上期下降至少 70%。
3. 同分类名次下降超过 10 位；必须在前后两期都确认该仓库的有效一级分类和排名，且分类一致，才计算分类内位次变化。
4. 最近 3 个可比的 7d 增长点严格逐点下降，即连续两次放缓；按仓库和日期同日去重，只保留同日最后一条，本期历史点由本期值替代后再取最近 3 点。
5. 观察清单项目在当前集合缺失。

组合触发可记录为“排名与增长同时下降”。这些是可核验事实信号，不是过时原因；原因推断与动作必须另列。指标直接支持“发生降温”的可信度，不能单独提高“为何降温”或“谁替代它”的可信度。榜单覆盖不足、周期不可比或只有观察清单缺失时，使用低可信度并继续观察。

替代关系采用五级：`直接替代`、`部分替代`、`注意力分流`、`同赛道共存`、`无明确替代者`。类别、场景、标签重合和新项目增速只能支持相似性或分流判断；直接替代必须同时有 canonical 直接证据。

canonical 直接证据仅限：迁移说明（`migration_guide`）、官方对比（`official_comparison`）、Release、Issue、社区讨论（`community_discussion`）。普通仓库说明页、相似描述、Star 增长或标签重合均不足以直接证明替代。

## 观察清单与持久化

观察清单固定 16 列。A–L 为人工列：仓库、项目名称、使用状态、优先级、使用场景、当前版本、开始关注日期、替代项目、是否检查更新、是否分析替代关系、负责人、备注。自动化只能原子更新 M–P：最近检查时间、最新版本、维护状态、建议动作；不得覆盖、移动、插行或重排人工列。

完整报告先保存归档与 `latest` 成对文件，再写月度 history，最后更新 Excel。任何报告保存失败都不得执行后置更新；history 失败时跳过 Excel；history 或 Excel 失败时保留已成功报告并明确为后置部分失败。意外异常不得降级成伪成功，也不得覆盖旧 `latest`。

所有业务日期与查询时间统一为 `Asia/Shanghai`。不得持久化 GitHub Token、Authorization/Cookie、请求头、带凭据 URL、环境变量值或异常中的敏感原文；报告只保留安全的来源名、周期、状态和业务字段。
